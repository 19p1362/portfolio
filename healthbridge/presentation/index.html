The problem in the code's own words

Patient data arrives as handwritten prescriptions, printed lab reports, WhatsApp photos of bills and scanned discharge summaries. None of it reaches the doctor, the nurse or the coordinator who needs it.

What drives the build

  • One record per patient, not six documents
  • Every clinic is a tenant — isolation is in the query layer, not a promise
  • Nothing is filed until a human confirms it

Built on

FastAPI 0.115 · Python 3.12 · SQLAlchemy 2 async · PostgreSQL (asyncpg) with SQLite for local dev · Alembic migrations · JWT scoped per tenant · React 18.3 + TypeScript 5.6 + Vite 6 · Flask dashboard for the agent loop.

Three layers, as implemented

  • Ingestion & API — document services OCR a photo or PDF, convert it, then serve it over a FHIR R4 API
  • Care orchestration — ten agents on a loop against the same database
  • Multi-tenant SaaS — organisation → users → patients, subscription tiers, role-based access

What it does

The clinic day, module by module

Clinical workflow

  • OPD registration + token queue — UHID issued, queue pushed over a WebSocket, doctor actions CALL_NEXT / SKIP / RECALL / COMPLETE
  • Vitals — typed observations with per-type units and reference ranges, latest-per-type for the chart
  • SOAP notes — ICD-10 search, autosave, version history, finalise, PDF export
  • Prescriptions — drug search, formulary detail, interaction checks, allergy warnings, dosing guidelines, then dispense in pharmacy
  • Labs, appointments, family care, risk scores — separate modules, one patient record

Ingestion & interoperability

  • Document ingestion service: photo or PDF → extracted fields → FHIR
  • FHIR R4 API plus a generic resource search/read endpoint
  • Connectors: ABDM, ABHA, Aadhaar eKYC, OpenMRS, FHIR standard
  • WhatsApp bridge for patient messaging

Code does the reading and the plumbing. A clinician still signs off every coded fact before it lands in the record.

Digital the right way · and who it is for

Ten agents, and the compliance that makes them usable

The ten agents in the orchestrator

patient intake · appointments · medication adherence · follow-up · labs · pharmacy · insurance · risk prediction · family care · voice care

Each runs on a schedule against the same patient record; the Flask dashboard shows status, patient stats and an activity feed.

Compliance, in code

Purpose-based consent, consent withdrawal, scheduled and executed erasure requests, field-level encryption (Fernet), an audit log with its own viewer screen, and an export centre.

Who it serves

  • Now: single clinics and hospitals in India — DPDP 2025 controls, ABDM/ABHA and Aadhaar eKYC connectors
  • Multi-clinic groups: tenant isolation with Free / Starter / Professional / Enterprise tiers
  • Later, the UK: the same loop, but it would need DTAC, DSPT, a DPIA and DCB0129 — none of which are claimed here

Why a practice can adopt it without ripping out its system

The API speaks FHIR R4 and exposes a resource search endpoint, so records can be read back out. Connectors to ABDM and OpenMRS already exist — the point is interoperation, not replacement.

How a pilot gets judged — three numbers

  • Minutes per incoming document — before versus after
  • Codes accepted unchanged — share a clinician keeps as proposed
  • Recalls closed by day 30 — not rolled into the next month

If those three do not move in thirty days, the pilot failed — and we say so first.
